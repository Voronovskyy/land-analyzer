# Науково-технічний звіт

## Інтелектуальна ГІС-система комплексного аналізу та оцінки земельних ділянок

**Виконавець:** Вороновський Данило
**Науковий керівник:** кафедра комп'ютерних наук
**Установа:** Лісотехнічний університет України
**Дата:** 13.08.2026

---

## 1. Постановка задачі

Традиційна оцінка земельних ділянок вимагає ручного збору даних із кількох
незалежних джерел: кадастрових реєстрів, метеорологічних баз, супутникових
знімків, даних OpenStreetMap та ін. Цей процес займає від кількох годин до
кількох днів і залежить від кваліфікації виконавця.

**Задача:** розробити ГІС-систему, яка автоматизує весь цикл аналізу — від
введення адреси чи кадастрового номера до готового PDF-звіту — і доповнює
кількісні показники якісними висновками великої мовної моделі (LLM).

**Уточнення задачі в ході роботи.** Початкова реалізація була настільною
(JavaFX). Обмеження такого підходу — потреба встановлення середовища на кожному
робочому місці — призвело до другого етапу: винесення системи у веб, з
публічним доступом через браузер без інсталяції.

## 2. Реалізована система

### 2.1 Загальні характеристики

- **Двоварiантна архітектура:** desktop (JavaFX 17) і web (Spring Boot 3.2 + React 19)
  поверх **спільного ядра аналізу**
- **Інтерфейс карти:** Leaflet.js — у WebView (desktop) та через iframe (web)
- **AI-модуль:** Claude API (Anthropic) — 6 незалежних ролей аналізу
- **Вихідний документ:** PDF змінного обсягу (OpenPDF + вбудований кириличний шрифт)
- **Зовнішні API:** 10 джерел даних (безкоштовні, крім Claude)
- **Розгортання:** Docker → Railway (бекенд), Vite → Vercel (фронтенд)

### 2.2 Джерела даних

| Джерело | Дані | Використання |
|---------|------|--------------|
| Open-Meteo | Клімат 30 д. + місячний і річний архів | Графіки погоди, агрокліматика |
| Open-Elevation | Висота над рівнем моря | Рельєф, ризик підтоплення, схили |
| OSM Overpass | Дороги, ЛЕП, водойми, POI | Інфраструктурний паспорт |
| Nominatim | Геокодування + reverse | Пошук ділянки, адресні дані |
| DOM.RIA | Ринкова ціна м² | Ринкова оцінка вартості |
| ПриватБанк / НБУ | Курс USD/UAH | Конвертація вартості |
| OSM / ESRI / OpenTopoMap / EOX | Картографічні тайли | 6 тематичних шарів |
| ДЗК (mock) | Кадастрові межі | Пошук за кадастровим номером |

### 2.3 Аналітичні модулі

**Площа та геометрія.** Полігон обчислюється формулою Shoelace (реалізація JTS).
Вхідні дані — межі з кадастру (GeoJSON) або точки, введені вручну.

**Оцінка вартості.** Базова: площа × ставка НГО (грн/м²). Ринкова: середня ціна м²
за DOM.RIA для локації; запит асинхронний, при недоступності лишається оцінка НГО.

**Коефіцієнт придатності (КП).** Зважена сума **шести** чинників: рельєф (15 %),
транспортна доступність (20 %), електромережі (15 %), водні ресурси (10 %),
екологічні ризики (20 %), клімат (20 %). Ваги нормалізуються за наявними даними,
тому відсутність окремого джерела не спотворює підсумок.

**Агрокліматика.** Індекс аридності Де Мартонна: `I = P / (T̄ + 10)`.
Класифікація: посушливий → напівпосушливий → напівгумідний → гумідний → гіпергумідний.

**Ризик підтоплення.** За абсолютною висотою: < 50 м — високий (низовина),
50–100 м — підвищений, 100–200 м — помірний, > 200 м — низький.

**Схили.** Кут ухилу оцінюється через перепад висот кутів ділянки (Elevation API)
та довжину діагоналі полігону (формула Haversine).

### 2.4 AI-аналіз (Claude)

Для кожного картографічного шару виконується незалежний запит із промтом
конкретної ролі:

| Шар | Роль | Фокус аналізу |
|-----|------|---------------|
| Схема інфраструктури | Урбаніст | Транспортна доступність, соціальна інфраструктура |
| Топографічний рельєф | Геоморфолог | Рельєфні умови будівництва |
| DEM | Гідролог | Ризики підтоплення, дренаж |
| NDVI | Агроеколог | Стан рослинності, придатність для агро |
| Супутниковий знімок | Інвестиційний аналітик | Потенціал розвитку, оточення |
| Карта схилів | Геотехнічний інженер | Ухили, ерозійний ризик, стабільність основи |

Промти зберігаються у `src/main/resources/prompts/*.md` — редагуються без
перекомпіляції.

## 3. Архітектурні рішення

### 3.1 Спільне ядро для двох варіантів запуску

Пакети `api/`, `model/` і більшість `util/` не залежать від способу запуску.
Розділення проходить лише там, де потрібна графіка:

| Задача | Desktop | Web |
|--------|---------|-----|
| Зображення карт | Знімок WebView | `StaticMapService` — зшивання тайлів |
| 3D-модель | JavaFX Canvas | `LandParcel3dImageRenderer` — Java2D |
| Оркестрація | `ReportCoordinator` | `WebReportService` |
| Збірка PDF | `PdfReportService` (спільний) | `PdfReportService` (спільний) |

Це дозволило додати веб-варіант без дублювання аналітичної логіки: обидва
конвеєри викликають ті самі розрахунки і той самий генератор PDF.

### 3.2 Асинхронний збір даних

```
Desktop: collectApiData → captureMapLayers → assemblePdf
Web:     збір даних + AI (паралельно) → карти → assemblePdf
```

Паралелізм скорочує збір даних з ~60 с (послідовно) до ~15 с. `CountDownLatch`
у desktop-фазі знімків гарантує завантаження тайлів перед скріншотом.

У веб-версії AI-запити стартують одночасно із завантаженням карт, тому AI
фактично «безкоштовний» за часом — він завершується, поки готуються зображення.

### 3.3 Стійкість до збоїв зовнішніх сервісів

Практична експлуатація показала, що більшість відмов — не в логіці системи, а в
зовнішніх залежностях. Реалізовано три рівні захисту:

| Механізм | Компонент | Деталі |
|----------|-----------|--------|
| Повтори з паузою | `ElevationApiService` | 5 спроб × 3 с, далі значення за замовчуванням |
| Вибіркові ретраї | `ClaudeAnalysisService` | 3 спроби з наростаючою затримкою; лише `429`/`5xx`/мережеві. `4xx` не повторюються — повтор їх не виправить |
| Обмеження паралелізму | `WebReportService` | Пул AI-запитів = 2: усі 6 одночасно впирались у ліміт одночасних з'єднань Anthropic |
| Деградація замість відмови | `OverpassApiService`, `DomRiaApiService` | Порожній/базовий результат замість переривання конвеєра |

### 3.4 Робота з неповним покриттям тайлових сервісів

Виявлено, що ESRI-сервіси повертають `HTTP 200` із зображенням-заглушкою
«Map data not yet available» для тайлів поза межами покриття даними, причому
глибина покриття **залежить від регіону**:

| Регіон | `World_Hillshade`: дані до |
|--------|---------------------------|
| Львів, південний степ | z16 |
| Київ, Карпати | z13 |

Оскільки фіксований ліміт зуму не працює, реалізовано `resolveDataZoom()`: проба
центрального тайла з покроковим зниженням зуму, доки не надійдуть реальні дані.
Заглушки розпізнаються за константним `ETag`. Невдала проба лишає зум незмінним,
тому механізм не впливає на інші тайл-провайдери.

### 3.5 Управління промтами поза кодом

`PromptLoader` читає MD-файли з classpath і кешує у `ConcurrentHashMap`.
Редагування ролі або тексту задачі не вимагає перекомпіляції.

### 3.6 Модульний PDF

`PdfReportService` делегує примітиви стилів у `PdfCellHelper` і конструкцію
таблиць карт у `MapExtrasBuilder` (обидва через `import static`). Це скоротило
основний файл з ~1100 до ~750 рядків та ізолювало зміни стилів.

## 4. Науковий внесок

1. **Інтеграція LLM у ГІС-конвеєр** — поєднання кількісних геопросторових метрик
   (площа, висота, NDVI, клімат) з якісним AI-аналізом у єдиному документі.

2. **Автоматизація повного циклу оцінки** — від координати до готового PDF за
   одну дію, без ручного збору даних.

3. **Верифікована мультиджерельність** — 10 незалежних API перехресно
   перевіряють одні й ті ж характеристики ділянки.

4. **Архітектура з двома точками входу над спільним ядром** — desktop і web
   дають ідентичні результати аналізу, відрізняючись лише способом отримання
   графіки; це знімає розбіжність між «локальною» та «онлайн» оцінкою.

5. **Відтворюваність** — кожен звіт містить метадані джерел; результати
   відтворювані для тих самих координат і дати запиту.

## 5. Практичні висновки з експлуатації

Розгортання у продакшн виявило клас проблем, невидимих при локальному тестуванні:

- **Зовнішній сервіс може «успішно» повернути беззмістовні дані.** Заглушка
  тайлів із кодом `200` — не помилка з погляду HTTP, але робить сторінку звіту
  порожньою. Перевірка лише коду відповіді недостатня.

- **Ретраї не універсальні.** Помилка розбору відповіді відтворювалась однаково
  на кожній спробі; ретраї лише втричі збільшували час до тієї самої відмови.
  Повторювати варто винятково транзиєнтні причини.

- **Підвищення надійності може створити нову відмову.** Додавання ретраїв
  подовжило генерацію настільки, що запити почали впиратись у клієнтський
  тайм-аут. Зміни, що додають затримки на сервері, треба узгоджувати з
  тайм-аутами клієнта.

- **Надмірне логування приховує причину збою.** Повні тіла відповідей Overpass
  (сотні KB) при паралельних запитах переплітались у потоці логів; реальний
  стек-трейс став видимим лише після обрізання дампів.

- **Headless-середовище відкидає приховані залежності.** Клас, що лише
  *посилається* на JavaFX-типи, не завантажується у Docker без JavaFX graphics —
  навіть якщо викликаний метод їх не використовує.

## 6. Обмеження та напрями розвитку

| Обмеження | Причина | Плановий розвиток |
|-----------|---------|-------------------|
| Кадастровий пошук — mock | API ДЗК потребує авторизації | Інтеграція з публічним API ДЗК |
| NDVI — тайловий шар | Немає чисельного NDVI-значення | Підключення Sentinel Hub API |
| Ринкова ціна — лише DOM.RIA | Одне джерело | Агрегація OLX, ЛУН, Rieltor.ua |
| Hillshade у частині регіонів — низька роздільність | Обмеження покриття ESRI | Альтернативне джерело DEM для таких зон |
| Claude API — платний | Anthropic pricing | Можливість перемикання на локальну LLM |
| Немає автотестів | Пріоритет функціональності | Модульні тести розрахункових утиліт |
